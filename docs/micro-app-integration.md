# 实战：子应用 A 接入完整练习

本文是练习说明，不代表接入功能已经实现或验证。每次只执行一个阶段，检查结果后再继续。

## 1. 练习目标与当前项目

任务：将主应用 `/apps/sub-a` 的占位页替换为真实子应用，完成路由、加载体验、主题同步和卸载验证。

2026-11-17 根据代码核对的起点：

| 项目                | 当前实现                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------- |
| `react-micro-app`   | Vite、React 19；`src/main.tsx` 已调用 `microApp.start()`；micro-app 声明版本为 `1.0.0-rc.31` |
| 主应用路由          | `src/router/index.tsx` 中 `/apps/sub-a` 仍使用 `PlaceholderPage`                             |
| `react-micro-child` | Webpack、React 18；开发服务配置端口为 3000；已有 Home、About 路由                            |
| 子应用入口          | `src/index.tsx` 已有 React root 渲染及 `unmount` 事件处理                                    |
| 子应用路由          | `src/App.tsx` 根据微前端环境决定 BrowserRouter 的 basename                                   |
| 主题通信            | 主应用 `src/theme.tsx` 广播 `platformTheme`；子应用同名文件订阅并清理监听                    |

这些是代码事实，不代表运行行为已通过验收。执行时仍应重新核实代码和依赖。

## 2. 模式和练习方式

| 阶段       | 模式             | 产出                           |
| ---------- | ---------------- | ------------------------------ |
| 调查代码   | Ask              | 现状、调用链、风险             |
| 拆解需求   | Plan             | 文件清单、方案、验收标准       |
| 最小接入   | Agent            | 能运行的挂载和路由             |
| 补齐体验   | Agent            | 加载、失败、重试、生命周期处理 |
| 审查       | Ask              | 有依据的问题清单               |
| 修复       | Agent            | 最小修复和验证结果             |
| 验收与总结 | 人工操作 + Agent | 验收记录、交付摘要             |

模式名称以你安装的 Cursor 版本为准。选择对应能力即可：只读分析、先规划、实际编辑。Markdown 是任务文档格式，本文件本身不等于已注册的 Skill。

## 3. 第 0 步：准备工作区

1. 在 Cursor 打开 `react-micro-app`。
2. 通过“添加文件夹到工作区”加入同级的 `react-micro-child`，确认 AI 能读取两个项目。
3. 查看两个项目 Git 状态，了解已有修改；需要时自行保存检查点。
4. 新建一个任务对话，后续尽量在该对话内推进。使用 `@` 或上下文选择器添加本文件及相关源码；确认选中了文件，不只是输入路径文本。

不必一次引用整个仓库。先引用入口、路由、主题、构建配置，让 AI 按需要继续搜索。

## 4. 第 1 步：Ask 调查代码

复制以下 Prompt：

```text
当前工作区包含 react-micro-app（主应用）和 react-micro-child（子应用）。
请阅读 docs/micro-app-integration.md，理解本次练习目标。

目标是将主应用 /apps/sub-a 的占位页替换为真实子应用，
保留独立运行能力，并验证路由、主题同步和卸载行为。

现在只调查代码，不修改文件。
检查：
1. 主应用 micro-app 初始化、路由及占位页。
2. 子应用开发服务地址、资源路径和跨域配置。
3. 子应用 BrowserRouter、basename 和微前端环境变量。
4. 子应用渲染、卸载和主题监听清理逻辑。
5. 两端主题通信链路。
6. 两端 package.json 的脚本和实际安装的相关依赖版本。

输出带文件路径的调用链、已完成能力、本次缺口及风险。
区分代码事实与推测，不套用其他微前端框架的 API。
如果无法读取另一个项目，明确指出，不要猜测。
```

检查点：回答应涉及主应用 `src/main.tsx`、`src/router/index.tsx`、`src/theme.tsx`，以及子应用 `src/index.tsx`、`src/App.tsx`、`src/theme.tsx`、`webpack.config.js`。

不满足时继续 Ask：

```text
请补充缺失部分，并引用实际源码说明。
目前先不提出实现已经成功的结论，也不要修改代码。
```

## 5. 第 2 步：Plan 制定方案

```text
根据刚才调查，为“子应用 A 接入”制定实施计划，暂不修改代码。

业务要求：
1. 主应用 /apps/sub-a 显示真实子应用。
2. 子应用 Home、About 可以切换，主应用布局和菜单保持正常。
3. 明确 micro-app 路由模式，再据此确定 URL、basename 和路由匹配方式。
   不预设嵌入后的子路由一定是 /apps/sub-a/about。
4. 切到工作台再返回，子应用仍正常显示。
5. localhost:3000 独立运行能力保留。
6. 主应用切换深浅模式和主题色，子应用同步更新。
7. 先换主题再进入子应用，也能获得最新主题。
8. 提供加载中、加载失败和重试入口。

约束：
- 不升级依赖、不引入新依赖、不关闭沙箱来绕过问题。
- 保留现有主题协议，只在发现缺陷时修复。
- 不修改子应用 B、其他学习示例，不覆盖已有修改。
- API 必须与实际安装的 micro-app 版本匹配；
  优先核实安装包类型和源码，必要时查对应版本官方文档。
- 不确定的 API 或配置先核实，不编造。

输出：路由及挂载方案、选择依据、修改文件与职责、
分阶段实施步骤、验收方法、尚未确认的问题。
```

你需要检查：是否解释了主子路由共存；是否复用主题实现；重试是否有实际重新加载机制；文件范围是否合理。

方案有问题时，继续在 Plan 中澄清。确认没有阻塞问题后，再切 Agent。

## 6. 第 3 步：Agent 完成最小接入

```text
按刚才确认的计划，先完成最小可用接入。

本阶段只做：
- /apps/sub-a 挂载真实子应用。
- 必要的主应用路由匹配、子应用 basename 调整。
- Home、About 导航和独立运行兼容。
暂不增加加载失败重试功能。

修改前查看两个项目 Git 状态，保留已有修改。
使用当前依赖版本支持的 API，不修改无关页面、不顺手重构。
完成后运行两端已有构建，说明修改内容与结果。
失败时区分已有问题、本次引入的问题和环境问题；
无法确定归因就明确说明，不要扩大修改范围。
未实际验证的浏览器行为不要声称通过。
```

在两个终端分别启动服务：

```bash
# 终端一：主应用目录
cd /Users/shentaoliu/Documents/learning/mianshi/react-micro-app
npm run dev
```

```bash
# 终端二：子应用目录
cd /Users/shentaoliu/Documents/learning/mianshi/react-micro-child
npm start
```

以终端实际输出地址为准。先打开子应用独立地址，再打开主应用，进入“应用管理 → 子应用 A”。检查 Home、About 导航、离开再返回。

如果此阶段不通过，先修复再继续。不要把基础挂载问题留到最后。

## 7. 第 4 步：Agent 补齐体验和生命周期

```text
最小接入已验证，继续完成加载体验与生命周期处理。

要求：
1. 加载期间显示加载状态。
2. 加载失败显示提示和重试入口。
3. 重试只影响当前子应用，不刷新整个主应用。
4. 检查离开页面后的 React root 销毁和监听清理。
5. 检查反复进入、离开是否产生重复监听或重复挂载。
6. 验证现有主题同步与晚挂载获取最新主题，只修复确认的缺陷。

依据当前版本生命周期 API 实现，说明监听及清理位置。
避免用大量 any 或关闭类型检查掩盖问题。
完成后运行受影响项目的构建和已有相关检查，
列出已验证、未验证场景，不把构建成功等同于浏览器验收成功。
```

检查点：失败提示能退出，重试确实重新加载，卸载清理针对当前实例，不误删其他监听。

## 8. 第 5 步：Ask 审查，Agent 修复

切 Ask：

```text
请审查本次任务相关 diff，暂不修改代码。
结合任务前的 Git 状态，区分本次变更和已有变更。

重点检查：
- 子应用内部导航是否导致主应用容器消失。
- micro-app 路由模式、basename、主应用路由匹配是否一致。
- 独立运行是否受影响。
- 重试是否真正重新加载，而非只清空错误文字。
- 卸载是否清理本实例注册的监听。
- 晚挂载是否能获得最新主题。
- 是否存在无关修改。

只报告有代码依据的问题，给出位置、触发条件、影响和修复建议。
不确定的问题标明所需验证，不为凑数量制造问题。
```

确认问题后切 Agent：

```text
修复刚才审查确认的问题，保持修改范围最小。
修复后运行受影响的检查，报告结果及剩余未验证项。
```

## 9. 第 6 步：人工验收与问题反馈

逐项执行并填写结果，初始状态均为“未验证”。

| 场景                                                     | 预期                               | 结果   |
| -------------------------------------------------------- | ---------------------------------- | ------ |
| 独立打开子应用                                           | Home、About 正常                   | 未验证 |
| 主应用进入子应用 A                                       | 真实子应用显示                     | 未验证 |
| 嵌入模式切 Home / About                                  | 内容正确、主应用布局及菜单正常     | 未验证 |
| 切工作台再返回，重复数次                                 | 无空白、重复挂载或重复响应         | 未验证 |
| 主应用切换深浅模式、主题色                               | 子应用同步更新                     | 未验证 |
| 先换主题，再进入子应用                                   | 子应用使用最新主题                 | 未验证 |
| 刷新嵌入模式的 About 页面                                | 按方案约定恢复路由或默认页，无空白 | 未验证 |
| 停止子服务后，在禁用缓存条件下重新加载主应用并进入子应用 | 显示失败提示，不一直加载           | 未验证 |
| 恢复子服务，点击重试                                     | 子应用恢复显示                     | 未验证 |

注意：已加载的子应用不会仅因服务停止就自动报错。失败场景需要触发新的资源加载；必要时使用浏览器网络请求阻断来稳定复现。

复现步骤：
1. ……
2. ……

实际结果：……
预期结果：……
相关控制台报错或失败请求：……

请先定位原因，再做最小修改。
检查修复是否影响独立运行和嵌入运行。
不清楚的信息先指出，不自行编造日志。

## 10. 第 7 步：Agent 整理真实交付记录

将自己的手动验收结果发给 AI，然后输入：

```text
请根据实际 diff、已运行检查和我提供的人工验收结果，
在 docs/micro-app-integration-result.md 整理本次交付记录。
如果文件已存在，先阅读并保留有效内容。

包含：
1. 原有行为和实现后的行为。
2. 关键修改、路由选择及原因。
3. 构建、检查和人工验收结果，区分各自来源。
4. 修复过的问题及原因。
5. 尚未验证的部分。

只记录真实完成的工作，不推测效率提升比例，不修改业务代码。
```

## 11. 练习时要观察什么

- AI 找错文件：补充上下文或明确项目路径。
- AI 猜业务规则：补充规则、边界和验收条件。
- AI 改动过大：收紧文件范围和当前阶段目标。
- AI 声称完成但页面不对：提供复现步骤、实际结果和预期结果。
- 对话过长或换了新对话：引用任务文档，补充已完成阶段、当前 diff 和未解决问题。

本次练习的核心是：提供上下文、制定可验证计划、分阶段实施、根据证据反馈。文档帮助保存这些信息，代码审查和实际验收负责确认结果。
