# AI 编程面试复习：React 微前端项目

本文围绕“通过 Prompt 工程提高开发效率、将复杂需求拆为 AI 可执行指令”整理练习题，不是面试题频率统计。参考回答需要结合自己的实际操作调整，不必逐字背诵。

## 一、项目事实与表达边界

当前练习使用 TRAE，界面提供 Chat 和 Agent。Chat 用于调查、规划和审查，Agent 用于实际实现与修复。

| 项目 | 本项目可举例的内容 |
| --- | --- |
| 主应用 react-micro-app | React 19、TypeScript、Ant Design 6、Vite，初始化 micro-app |
| 子应用 react-micro-child | React 18、TypeScript、Ant Design 5、Webpack，有 Home、About 和 Redux 计数功能 |
| 接入功能 | 主应用已有 SubAppA 组件和对应路由，包含加载状态、错误提示、重试代码 |
| 主题 | 两端各自有 SkinProvider，通过 platformTheme 传递配置 |
| AI 项目规则 | 两端分别配置 .trae/rules/project.md |
| 主应用 Skill | micro-app-integration，配套验收清单 |
| 子应用 Skill | micro-app-child-maintenance，关注独立和嵌入双模式 |

这里描述的是源码和配置，不代表全部运行验收已通过。没有记录的耗时、效率比例、缺陷数量和浏览器验证结果，不要作为完成事实讲述。规则与 Skill 文件存在，也不等于已在 TRAE 中确认自动加载。

相关资料：[接入练习](micro-app-integration.md)、[主应用配置说明](trae-rules-and-skills.md)。

## 二、开场：你如何使用 AI 编程？

### 1. 平时用 AI 做什么？

**参考回答：**

我主要使用 TRAE 辅助代码调查、需求拆解、实现和审查。在 React 微前端项目中，我把子应用接入拆成现状分析、路由方案、最小接入、加载重试和验收几个阶段。AI 负责辅助检索和实现，我负责明确业务边界、检查 diff，并确认实际运行结果。

**追问准备：** 能现场指出入口、路由、主题和 Skill 文件；解释哪些内容自己执行过，哪些仍在练习。

### 2. 相比直接对话生成代码，你的方法有什么变化？

**参考回答：**

以前更多是描述一个功能，让 AI 直接写。现在会先提供相关代码上下文，明确修改范围和验收条件，再分阶段推进。比如主子应用的 React 和 Ant Design 版本不同，我会要求分别核实依赖，避免生成另一端才能使用的 API。

## 三、Prompt 编写与需求拆解

### 3. 什么是高质量代码生成 Prompt？

**参考回答：**

我关注五项信息：项目上下文、任务目标、业务规则、修改约束、验收标准。重点是减少影响实现的歧义，而不是让提示词看起来复杂。

**项目示例：**

```text
任务：为主应用接入现有 React 子应用。
先阅读两端入口、路由、主题和构建配置。

要求：保留独立运行；内部路由不破坏主应用布局；
支持加载、失败与重试；复用现有主题通信。

约束：使用实际安装版本支持的 API，保留已有修改，
不升级依赖、不关闭沙箱、不改无关页面。

先给出涉及文件、路由方案和验收场景，暂不编码。
```

### 4. Prompt 越长越好吗？

**参考回答：**

不是。简单修改只需要目标和约束，复杂任务才需要更多背景。大量无关信息会增加干扰。我会让 AI 先调查相关代码，再补齐影响实现的业务规则，避免重复粘贴整个项目。

### 5. 如何把复杂需求拆给 AI？

**参考回答：**

按可独立验证的结果拆分。子应用接入先调查入口和资源配置，再确定路由模式，完成最小挂载与导航，然后补加载重试、通信和卸载验证。每一步有明确产出，出现问题时能缩小定位范围。

| 阶段 | 产出 | 主要检查 |
| --- | --- | --- |
| 调查 | 调用链与缺口 | 是否依据真实源码 |
| 规划 | 路由与挂载方案 | 版本、模式、basename 是否协调 |
| 最小接入 | 独立和嵌入入口 | 页面显示、内部导航 |
| 补齐体验 | 加载、错误、重试 | 是否真正恢复加载 |
| 验收 | 检查结果与未验证项 | 不用静态推断替代运行证据 |

### 6. 如何给 AI 提供上下文？

**参考回答：**

先提供任务文档和关键文件，让它继续搜索必要依赖。我的项目重点是主应用入口、路由、SubAppA，以及子应用入口、App、主题和 Webpack 配置。跨项目时明确两端目录；新对话则补充已完成阶段、当前 diff 和未解决问题。

**追问：文档里的现状过时怎么办？** 文档提供任务目标，当前源码用于确认现状。要求 AI 识别差异，不能把历史起点直接作为当前事实。

## 四、代码质量与问题定位

### 7. AI 写完以后，你如何保证质量？

**参考回答：**

先审查 diff 和修改范围，再核实 API 与实际依赖版本，运行适用的构建和类型检查，最后验证业务行为。主应用 build 包含 tsc，而子应用当前通过 Babel 打包，不能认为两端 build 对类型检查的覆盖相同。浏览器中的路由和生命周期还要单独验证。

### 8. AI 会编造 API，你怎么避免？

**参考回答：**

明确要求依据实际安装包类型、源码或对应版本官方文档。比如本项目使用 micro-app 的特定 rc 版本，我不会让它直接照最新示例实现重试或路由。找不到依据时先标记待核实，再决定方案。

### 9. AI 反复修不好一个问题怎么办？

**参考回答：**

我会停止笼统地说“再改一下”，补充运行模式、URL、复现步骤、预期、实际结果和报错。先验证关键假设、缩小问题，再要求最小修改。多轮没有进展时，我自己调试和定位，AI 辅助分析或实现，不无限重写。

**反馈示例（假设场景，不是已发生的项目缺陷）：**

```text
嵌入模式下，从 Home 点击 About 后页面空白。
预期是切换子页面且主应用容器保留。
请结合实际 URL、路由模式、basename 和主应用路由匹配定位。
先指出证据，再做最小修复，并检查独立运行是否受影响。
```

### 10. 让另一个 AI 审查，是否就足够？

**参考回答：**

不够。AI 审查能补充线索，但可能重复同样的错误假设。我会要求问题有代码位置、触发条件和影响，再结合检查命令和运行行为确认。模型说“没有问题”不是验收证据。

### 11. 哪些部分不能完全交给 AI？

**参考回答：**

业务边界、架构取舍、权限与数据处理、最终验收需要开发者负责。AI 可以提出建议和实现初稿，但我需要能解释关键修改，并检查它是否符合需求。没有理解的代码不能仅因能运行就接受。

## 五、Rules、Skill 与上下文管理

### 12. Prompt、Rules、Skill 和任务文档有什么区别？

| 类型 | 作用 | 项目例子 |
| --- | --- | --- |
| Prompt | 本轮具体指令 | 排查 About 路由白屏 |
| Rules | 项目长期约束 | 保留已有修改、遵循各自依赖版本 |
| Skill | 一类任务的可复用流程 | 微前端接入、子应用双模式维护 |
| 任务文档 | 本次目标、步骤和验收 | docs/micro-app-integration.md |
| Skill 参考资料 | 按需展开的细节 | references/acceptance.md |

**参考回答：**

它们可以都用 Markdown 写，但用途和加载方式不同。Markdown 只是格式。我把长期约束放进 Rules，把接入方法放进 Skill，把这次任务细节保留在任务文档里，避免所有信息混成一个超长提示词。

### 13. 为什么需要 Skill？是不是把 Prompt 保存起来？

**参考回答：**

核心是将某类任务的方法封装为可复用流程，还要写清适用场景和需要调查的输入。我的接入 Skill 不固定应用名、端口和路由，要求先确认当前项目再执行；详细验收放在 references 中。它不是把某次代码生成指令原样复制保存。

### 14. 如何确认 Skill 已被使用？

**参考回答：**

先在工具设置中确认识别和启用，再用只读任务试用，检查可见的读取记录是否涉及 Skill 和需要的参考文件。明确点名调用与自动匹配分别测试，不能仅凭模型声称“已加载”判断成功。

### 15. 两个项目的规则会冲突吗？

**参考回答：**

可能出现适用范围混淆，因此规则要清楚限定所属项目。主应用与子应用版本不同，各自文件遵循各自技术栈。联合任务以主应用接入 Skill 为主流程，需要子应用适配时再参考子应用 Skill，避免两套完整流程重复执行。

### 16. acceptance.md 会自动完成测试吗？

**参考回答：**

不会，它是检查清单。AI 根据可用工具执行构建或浏览器操作；没有对应能力的交互场景需要人工验证。结果要区分工具实测、静态检查、用户验收和未验证，不能因为清单存在就认为已经通过。

## 六、结合微前端的技术追问

### 17. 路由适配为什么容易出错？

**参考回答：**

需要同时理解基座路由模式、子应用 basename 和内部导航。不能预设子应用 About 一定对应基座的 pathname 子路径；应检查当前 micro-app 模式与真实 URL，再验证跳转、刷新、前进后退和容器是否保留。

### 18. 为什么不能直接跨应用共享 React Context？

**参考回答：**

两端有独立 React 根和 Provider，不能指望主应用 Context 自动跨越到子应用。当前项目传递可序列化的 platformTheme 配置，两端各自应用 Ant Design 主题。不同 origin 的 localStorage 也不能替代跨应用实时通信。

**追问准备：** 解释晚挂载如何读取最新配置、外部数据如何校验、监听如何清理。按当前源码回答，不凭记忆编造 API。

### 19. 为什么“有 unmount 代码”还需要运行验收？

**参考回答：**

静态代码只能说明存在处理逻辑，还需要确认框架是否触发对应事件、重挂载如何执行、订阅是否重复。卸载重建、缓存和保活不是同一行为，必须结合实际配置验证。

### 20. 如何验证失败重试？

**参考回答：**

要触发真实的新资源加载失败。停止服务不会让已加载页面自动报错，我会在禁用缓存或请求阻断条件下复现，恢复服务后点重试，确认实际重新加载且主应用没有整体刷新。具体缓存与销毁机制需要按当前版本核实。

## 七、效率、经验与可信度

### 21. 如何证明 AI 提升效率？

**参考回答：**

目前我观察到代码检索、方案初稿和重复实现方面的帮助，但没有足够记录支持具体百分比。后续会记录任务范围、总耗时、提示与审查时间、返工次数和缺陷情况，在质量可比的前提下评估，不只统计生成代码的速度。

### 22. 讲一个 AI 生成错误、你纠正的案例

这道题需要真实经历。按以下结构补充，不把假设场景当成事实：

- 任务背景：我当时要完成什么？
- AI 输出：具体生成了什么实现？
- 发现依据：哪条日志、请求或复现操作表明不对？
- 原因：缺失上下文、版本误用、业务误解还是实现错误？
- 纠正过程：我如何补充信息、定位或修改？
- 验证结果：实际执行了什么？
- 经验沉淀：是否需要改 Prompt、规则或 Skill，为什么？

### 23. 这些规则和 Skill 是自己写的吗？

**参考回答：**

初版由 AI 根据我的项目和要求辅助生成，我负责理解适用范围并逐步试用、验证和修订。我不会把文件生成等同于效果已经证明，也不会把 AI 辅助编写描述成完全手写。

## 八、1～2 分钟项目陈述

> 我在 React 微前端练习项目中使用 TRAE 辅助开发。主应用使用 React 19、Vite，子应用使用 React 18、Webpack，因此我特别注意让 AI 区分两端依赖与配置。
>
> 在子应用接入任务中，我把工作拆成代码调查、路由方案、最小接入、加载重试和验收几个阶段。Prompt 会明确相关文件、业务行为、修改边界和验收条件，避免只说“帮我实现”。
>
> 我也配置了两端项目规则，并整理了接入和子应用维护 Skill，将通用流程与本次任务需求分开。生成结果需要检查 diff、核实版本 API、运行适用检查，再验证双模式路由、主题和卸载等行为。
>
> 目前我正在积累实际验收与问题案例。效率方面还没有可靠百分比，我更关注任务总耗时和返工情况，并对最终结果负责。

根据真实进度改写，尤其是“已执行检查”“已验证场景”和实际问题案例。

## 九、面试前自查

- [ ] 能指出并解释主子应用入口、路由、主题通信和卸载代码。
- [ ] 能现场写出包含上下文、边界和验收的 Prompt。
- [ ] 能解释任务为什么这样拆，而不是只背步骤。
- [ ] 能说明 Rules、Skill、任务文档和参考资料的区别。
- [ ] 已核实 TRAE 是否识别配置，哪些调用方式实际试过。
- [ ] 准备一个真实的问题定位案例，不编造经历。
- [ ] 有一份真实检查和验收记录，知道哪些尚未验证。
- [ ] 不虚报效率比例，能解释自己对生成代码的判断依据。

复习时优先练习口头回答，再打开源码核对。关键是能解释自己的决策、证据和修改，而不是记住术语。
